\section{System Architecture Overview}
\label{sec:system-architecture-overview}

Stockrium follows a client--server architecture supported by asynchronous data-acquisition services. The React Native mobile application is the primary interface for individual investors, while an internal web dashboard allows administrators to run controlled analysis and backtesting. Both clients communicate with a FastAPI backend that centralizes authentication, business logic, data access, AI workflows, and standardized API responses.

Supabase PostgreSQL stores the application's durable business, market, financial, news, and conversational data, while Redis maintains temporary authentication and verification state. Separate workers collect and prepare information from external sources such as SSI and online news providers. This separation keeps provider credentials and processing logic outside the clients and allows most user requests to read normalized data that have already been prepared.

\subsection{Architectural Requirements}
\label{subsec:architectural-requirements}

The architecture must support mobile market exploration, configurable multi-agent analysis, conversational queries, and administrative backtesting without coupling these responsibilities to the user interface. It must integrate heterogeneous financial evidence, protect user-specific and administrative operations, preserve conversation state, and update market and news data without blocking normal requests. Maintainability is supported by separating presentation, domain services, AI workflows, and data access. Most importantly, the architecture reflects the application's decision-support scope: no component connects to a brokerage account, transfers funds, or executes securities transactions.

The presentation layer contains the mobile application and the internal administrative dashboard. These clients handle interaction and visualization, while protected operations and financial-processing logic remain in the backend. The web dashboard is used only by administrators and is not deployed as a public web version of Stockrium.

FastAPI forms the application boundary. Routes validate requests and authentication information before delegating work to domain services for accounts, market data, company information, fundamentals, articles, user preferences, and other application functions. This organization allows the same prepared data and services to support mobile screens, analytical workflows, chatbot tools, and backtesting without embedding database logic in the clients.

The AI layer contains separate workflows for stock analysis and conversational assistance, together with the historical backtesting subsystem. The stock-analysis graph combines technical, fundamental, and news perspectives into a structured result. The chatbot maintains multi-turn state, whereas backtesting applies analysis logic to historical data. Keeping these execution models separate prevents conversational context or experiment state from affecting an ordinary stock-analysis request.

The data-integration and persistence layers isolate the application from provider-specific formats. Acquisition workers normalize market prices, company information, financial statements, and articles before storing them in Supabase. Redis is reserved for temporary authentication state, and Supabase Storage holds backtest artifacts. The detailed data model, acquisition pipelines, and storage responsibilities are presented later in this chapter.

\subsection{End-to-End Request Flows}
\label{subsec:end-to-end-request-flows}

For a typical synchronous request, a client sends an authenticated request to FastAPI. The corresponding route validates the input and invokes either a domain service or an AI workflow. The selected component reads prepared data from the persistence layer, performs the required processing, and returns a standardized response for display. Stock-analysis requests additionally coordinate the selected analytical perspectives, while conversational requests load and update their associated chat state. Administrative backtests follow the same protected boundary but operate over historical data and produce experiment results rather than live transactions.

Data acquisition follows an asynchronous path. Market and article workers retrieve information from external providers, normalize it, and upsert it into Supabase according to their schedules. The user-facing clients therefore do not communicate directly with SSI, Serper, or article websites. This design centralizes credentials and data preparation while keeping interactive requests comparatively lightweight.

Overall, Stockrium combines thin client applications, a validated FastAPI boundary, modular domain and AI services, scheduled acquisition workers, and storage selected according to data lifetime. The following sections describe each of these areas in greater detail.
