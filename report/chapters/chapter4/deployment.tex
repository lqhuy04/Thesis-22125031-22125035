\section{Deployment}
\label{sec:deployment}

Stockrium uses separate deployment services for its server-side workloads, scheduled database operations, and mobile application package. This separation allows each component to run in an environment suited to its execution model without placing data-refresh work inside an interactive API request.

\textbf{Railway.} Railway provides container-based deployment targets for persistent applications and scheduled workloads, together with build commands, runtime configuration, logs, and metrics \cite{railwayServices2026}. Stockrium uses one Railway service to run the FastAPI backend and expose the HTTPS API consumed by the mobile application. A second, independent service runs the financial-news updater. Its scheduler periodically executes the macroeconomic, category, and stock article pipelines, which collect articles, generate summaries and sentiment labels, and store the prepared records in Supabase. Keeping this workload separate prevents a long crawl and its model calls from occupying API workers or being duplicated when the API service restarts or scales.

\textbf{Supabase Cron Jobs.} Supabase Cron uses PostgreSQL scheduling to execute recurring SQL operations, database functions, or HTTP requests such as calls to Supabase Edge Functions \cite{supabaseCron2026}. In Stockrium, these jobs invoke two Edge Functions on a defined schedule to refresh \texttt{Current\_Stock\_Price} and \texttt{Current\_Market\_Index}. The former supplies latest-price snapshots used by market lists, watchlists, search-history views, and current-price cards; the latter supplies the current VN30 and VN100 index state. The database-side schedule is distinct from the Python market-data workers that maintain historical stock candles and index-value series, so both mechanisms are required to keep their respective data representations current.

\textbf{Expo Application Services.} EAS Build is Expo's hosted service for producing installable binaries for Expo and React Native applications \cite{expoEASBuild2026}. Stockrium uses EAS Build to compile and package the mobile client as an Android application package (APK) for installation and testing. EAS is therefore responsible for producing the distributable mobile artifact, whereas the application's runtime API remains hosted on Railway. The internal experimentation and backtesting web interface is not deployed as a separate public application.
