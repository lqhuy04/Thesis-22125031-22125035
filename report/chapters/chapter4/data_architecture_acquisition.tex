\section{Data Architecture and Acquisition Pipelines}
\label{sec:data-architecture-acquisition}

Stockrium depends on data with substantially different lifecycles. User preferences change through application requests; prices change throughout a trading session; financial statements are collected periodically through offline acquisition utilities; articles are refreshed weekly; and chatbot checkpoints grow one conversation turn at a time. The data architecture therefore separates persistent relational records, generated file artifacts, short-lived security state, and device-local credentials. It also separates acquisition work from interactive API execution: the mobile application reads normalized data through the backend but does not start a Selenium crawler, an SSI stream, or a news-collection job.

\subsection{Supabase Data Model}
\label{subsec:supabase-data-model}

PostgreSQL is exposed through Supabase rather than replaced by a proprietary document model, allowing the application to use keys, constraints, relations, pagination, and conflict-aware upserts \cite{supabaseDatabase2026}. The central entity is \texttt{Stock}. Company and financial tables use \texttt{stock\_id} to associate records with a listed security. Annual financial records are organized as stock--year observations. \texttt{FA\_Summary} and \texttt{BI\_Profile} provide stock-level text or profile information, while one company can have multiple leader and subsidiary records. The stock price tables use \texttt{(stock\_id, trading\_time)} as their composite identity, and \texttt{Current\_Stock\_Price} maintains the latest record for each \texttt{stock\_id}. \texttt{MarketIndex} defines the supported indices, \texttt{Stock\_MarketIndex} stores their constituents, \texttt{MarketIndex\_Value\_1m} and \texttt{MarketIndex\_Value\_1d} use \texttt{(market\_index\_id, trading\_time)} for historical values, and \texttt{Current\_Market\_Index} stores the corresponding current market state.

Account data is separated from market data. \texttt{Favorite} records the stocks selected by each user for later monitoring, while \texttt{Search\_History} uses the same user and stock references and retains the six most recent unique stocks. \texttt{RiskAppetite} stores one current investment-horizon profile for each user. These relations allow the backend to enrich lightweight personalization records with company profiles and current prices without duplicating market data in user-owned tables.

Four association tables represent many-to-many relationships. \texttt{Stock\_MarketIndex} records index constituents, \texttt{Category\_Stock} records the classifications to which a stock belongs, and \texttt{Article\_Stock} and \texttt{Article\_Category} associate one article with multiple securities or categories without copying its content. \texttt{FA\_Industry\_Aggregate} is identified by \texttt{(category\_id, year)} and uses the ICB category derived from \texttt{BI\_Profile.icb\_code} to store annual peer medians for comparison with company indicators.

Chat metadata and conversational content are deliberately separated. \texttt{chat\_sessions} associates each conversation with its user, title, and timestamps. LangGraph's PostgreSQL saver uses the session identifier as its \texttt{thread\_id} and stores message-bearing graph states in the checkpoint tables \cite{langgraphPersistence2026}. Deleting a conversation removes its checkpoint writes, blobs, checkpoints, and session record, while \texttt{checkpoint\_migrations} remains framework metadata.

\subsection{Market Price Acquisition Pipeline}
\label{subsec:market-price-acquisition}

The \texttt{update\_stock\_price/} subsystem supports two acquisition modes: historical initialization and daily live operation. Initialization scripts obtain an SSI access token and backfill stock OHLCV data for the current VN100 constituent set together with historical values for VN30 and VN100. Daily initialization is divided into 30-day requests because of the upstream API limit and currently loads approximately five years. One-minute initialization uses three consecutive 30-day windows, giving approximately 90 days of retained intraday history. Stock rows are normalized with \texttt{stock\_id}, \texttt{trading\_time}, OHLC, and volume fields before deduplication and upsert on \texttt{(stock\_id, trading\_time)}. Index rows contain \texttt{market\_index\_id}, \texttt{trading\_time}, and \texttt{value} and are upserted on \texttt{(market\_index\_id, trading\_time)}. Requests are paced by approximately 1.1 seconds between provider calls to reduce SSI rate-limit pressure.

Live acquisition is controlled by a long-running scheduler using Vietnam time (UTC+7). On Monday through Friday, it ensures that four child processes are running from 09:00 inclusive until 15:00 exclusive: one-minute and daily stock-price WebSocket workers together with one-minute and daily market-index HTTP pollers. The scheduler checks their state every 30 seconds and restarts a child process if it has exited unexpectedly. At 15:00, it sends an interrupt signal to each process, waits for a graceful shutdown, and forcibly stops a process only if it does not exit within the timeout.

The one-minute stock worker subscribes only to SSI bar messages for the current VN100 stock mapping and aggregates incoming ticks in an in-memory candle buffer. The key is the pair of \texttt{stock\_id} and minute. The first tick establishes open, high, low, close, and volume; later ticks update the high and low, replace the close, and accumulate volume. Closed minutes are flushed from a separate loop so network I/O to Supabase does not block the SSI callback. The current open minute is not written during shutdown because it is incomplete.

Before a stock-price message is admitted to a live candle buffer, a shared preprocessing component parses every OHLCV field as a finite number instead of replacing a missing or malformed value with zero. Stock prices are converted from the SSI unit by the existing \(1/1000\) multiplier. A row is accepted only when all four prices are positive, the high is not below the open, low, or close, the low is not above the open, high, or close, and volume is strictly positive. Consequently, invalid live stock messages are discarded before they can establish or contaminate a buffered candle. The index pollers follow a separate normalization path: they obtain VN30 and VN100 values from SSI's \texttt{IntradayOhlc} endpoint, retain the latest point observed within each minute, and store the index value without applying the stock OHLCV rules or stock price-unit conversion.

The daily stock worker subscribes to the same stock bar stream but accumulates one current-session record per \texttt{stock\_id} in \texttt{Stock\_Price\_1d}. In parallel, the one-minute index poller writes normalized VN30 and VN100 observations to \texttt{MarketIndex\_Value\_1m}; the daily index poller converts the latest intraday value into the current session's 14:45 record in \texttt{MarketIndex\_Value\_1d}. These historical series are distinct from \texttt{Current\_Market\_Index}, which is refreshed by a scheduled Edge Function with latest index totals, change, breadth, and turnover fields for application cards.

At or after 15:05, the scheduler runs four reconciliation jobs exactly once for the date and, importantly, runs them sequentially: stock one-minute, stock daily, index one-minute, and index daily. Both one-minute jobs re-fetch a two-day lookback and retain 90 days; both daily jobs reconcile a three-day lookback and retain five years. The stock jobs apply the shared OHLCV validation rules, while the index jobs normalize SSI values for VN30 and VN100. Valid stock rows are deduplicated and upserted on \texttt{(stock\_id, trading\_time)}, and valid index rows are upserted on \texttt{(market\_index\_id, trading\_time)}. When a reconciled row has the same key as a provisional live row, the conflict-aware upsert replaces the live value with the SSI result. This correction is key-specific: an upsert does not delete a live-only timestamp that is absent from the post-session response. Sequential execution prevents the four provider-intensive jobs from making SSI requests simultaneously and exceeding provider limits.

The preprocessing rules do not reject a row solely because its price differs sharply from the previous session. Such a discontinuity may be legitimate, for example on the ex-date of a share dividend or stock split, and percentage-based outlier removal could therefore erase valid market information. The current acquisition pipeline stores raw exchange OHLCV values and does not yet associate them with corporate-action adjustment factors. Producing an adjusted price series for return calculation and backtesting consequently remains a separate data-enrichment requirement rather than part of the present validity filter.

Two deployed Supabase Edge Functions maintain the latest-state read models independently of the Python processes in \texttt{update\_stock\_price/}. The current-price function resolves the VN100 constituents through \texttt{MarketIndex}, \texttt{Stock\_MarketIndex}, and \texttt{Stock}; requests the current HOSE rows from SSI's \texttt{DailyStockPrice} endpoint; converts the SSI price unit; and upserts the matched values into \texttt{Current\_Stock\_Price} on \texttt{stock\_id}. The stored fields include the current, reference, ceiling, and floor prices, absolute and percentage changes, and matched volume and value. Consequently, market lists, favorites, search history, and current-price cards can read a compact snapshot without scanning historical candle tables.

The current-market-index function updates VN30 and VN100. For each configured index, it obtains totals and change fields from SSI \texttt{DailyIndex}, takes the latest index value from \texttt{IntradayOhlc}, and derives advances, unchanged stocks, and declines by joining \texttt{Stock\_MarketIndex} membership with \texttt{Current\_Stock\_Price.price\_change}. It then upserts one row per index into \texttt{Current\_Market\_Index} on \texttt{market\_index\_id}. SSI calls are serialized with an approximately 1.1-second interval, and an authentication failure causes the function to obtain a new SSI token and retry the request.

Supabase Cron invokes both Edge Functions through scheduled HTTP requests \cite{supabaseCron2026}. Each function has two weekday execution windows: \texttt{* 2-4 * * 1-5} and \texttt{* 6-7 * * 1-5} in UTC, corresponding to every minute from 09:00 through 11:59 and from 13:00 through 14:59 in Vietnam time. These managed jobs complement rather than replace the Python scheduler: the Python workers maintain historical candles and live streams, whereas the Edge Functions refresh the latest stock and index snapshots used by the application. Deployment therefore requires both scheduling mechanisms.

The scheduler's trading-day test currently recognizes weekdays rather than an exchange-holiday calendar. On a weekday market holiday it may start streams and later execute reconciliation even though no session occurred. Upserts and empty-response handling reduce the risk of corrupting stored candles, but a production version should consume an official Vietnamese exchange calendar.

\subsection{Company and Fundamental Data Pipeline}
\label{subsec:company-fundamental-pipeline}

Company and financial acquisition is an offline data-preparation process. It is not invoked from a mobile request because browser automation, file downloads, report parsing, and multi-company imports are too slow and operationally fragile for an interactive API path. The backend serves only data that has already been normalized and stored.

Company-profile collection uses Selenium WebDriver to open SSI iBoard, establish an authenticated browser session, search for a stock, enter dynamically loaded page regions, and parse company information. The crawler obtains profile attributes, leadership records, and subsidiaries or associates. A stock is first resolved through \texttt{Stock}; profile fields are updated in \texttt{BI\_Profile}. Leadership and subsidiary collections are replaced for the stock by deleting their previous rows and inserting the newly observed records. The crawler supports batch operation from symbols already present in \texttt{BI\_Profile} and maintains progress so a long run can resume after a browser or page failure. The use of Selenium for a dynamically rendered source follows the browser-automation rationale introduced in Chapter 2 \cite{seleniumWebDriver2025}.

A separate SSI financial downloader navigates the fundamental-analysis interface and triggers downloads for the balance sheet, income statement, cash-flow statement, and financial-indicator sections. Excel files are converted where necessary, and pandas transforms the downloaded wide layouts into tidy records containing one symbol and financial year per row. Processing removes unnamed or empty columns, normalizes Vietnamese labels into stable database fields, converts numerical values, drops empty trailing years, and serializes missing values as database nulls. The current application schema associates the processed records with \texttt{Stock.id} and stores them in the corresponding \texttt{FA\_*} tables. Upserts use the stock--year identity so rerunning an import corrects or completes existing observations instead of blindly duplicating them. pandas and its workbook engines are suited to this conversion of heterogeneous tabular reports \cite{pandasIO2026}.

Industry aggregation is performed after company profiles and financial indicators are available. The utility maps detailed \texttt{BI\_Profile.icb\_code} values to an ICB industry identifier, groups \texttt{FA\_Indicator} records by industry and year, and computes the median of every available metric while ignoring missing values. It also counts the contributing stocks. Results are upserted into \texttt{FA\_Industry\_Aggregate} on \texttt{(category\_id, year)}. The current utility retains the configured 2021--2025 range and removes obsolete years or invalid category identifiers. Precomputation moves repeated peer aggregation out of user requests and lets the fundamental-analysis node compare a company with a consistent industry benchmark.

Fundamental summaries are also generated as an offline maintenance operation rather than during a mobile request. The active backend reads \texttt{FA\_Summary} by \texttt{stock\_id}. The OpenAI batch utility performs multi-year evidence retrieval, retry, pacing, and skip-existing behavior before persisting the generated text. Its source code retains the earlier name \texttt{fundamental\_analysis\_summary} and earlier lower-case financial-table names; these identifiers refer to the predecessor schema that was later renamed to the active \texttt{FA\_*} tables. They are treated as one logical dataset in this report, with \texttt{FA\_Summary} used consistently as the current name.

\subsection{Financial News Pipeline}
\label{subsec:financial-news-pipeline}

The \texttt{update\_articles/} subsystem separates initial collection from periodic refresh. Initial scripts backfill stock-specific, macroeconomic, and category-level news over a longer search horizon and include checkpoint files for resuming multi-page collection. Update scripts request only the latest week and perform one current search page for each configured topic, category, or stock. This distinction reduces the cost of routine updates while preserving a path for initializing a new deployment.

For each target, the pipeline submits a Vietnamese news query to the Serper news endpoint. A result supplies candidate metadata and a source URL. Newspaper3k then downloads the selected page and extracts the article title, body, publication information, and representative image when available. Failed or empty pages are skipped because an inaccessible URL should not produce an article containing only generated text.

The extracted article is passed to \texttt{gpt-4o-mini} with a typed response schema. Stock queries request a short Vietnamese summary and a positive, neutral, or negative label from the perspective of the named security. Category queries use the corresponding industry perspective, while macroeconomic articles receive a general market label. Invalid labels are normalized to neutral before insertion. The original content and source metadata remain in \texttt{Article}, so the summary does not replace the source evidence.

Duplicate prevention occurs at two levels. Existing links are loaded before extraction so a known URL can be skipped without another model call. The insertion path checks again before creating the article. After an article exists, the pipeline checks the relevant join table before inserting \texttt{Article\_Stock} or \texttt{Article\_Category}. The same article can consequently be reused across associations without duplicated content or duplicate join rows. General macroeconomic articles can remain unassociated with an individual security.

The production article scheduler uses Vietnam time and executes once per ISO week on Saturday at 23:00. It runs \texttt{update\_macro\_articles.py}, \texttt{update\_category\_articles.py}, and \texttt{update\_stock\_articles.py} sequentially, waiting for each process to finish. A process-local week key prevents a second execution during the same uninterrupted scheduler run. Even if a service restart causes a repeated attempt, link-level duplicate checks make the update substantially idempotent. This weekly article refresh is not one of the Supabase Cron jobs described in the market-price pipeline: those jobs invoke the two Edge Functions that refresh \texttt{Current\_Stock\_Price} and \texttt{Current\_Market\_Index} during weekday trading hours.

\subsection{Storage Responsibilities}
\label{subsec:storage-responsibilities}

Not every value belongs in the same storage mechanism. Stockrium separates durable relational records, file-based experiment artifacts, temporary server-side security state, and device-local secrets according to their lifecycle and access requirements.

\textbf{Supabase PostgreSQL.} Supabase PostgreSQL is the authoritative store for durable relational data, including accounts, personalization records, the security directory, market candles and snapshots, company profiles, financial records, industry aggregates, articles, classifications, chat-session metadata, and LangGraph checkpoints. Domain services access ordinary application records through Supabase PostgREST, while pooled PostgreSQL connections support checkpoint persistence and controlled chatbot queries. Clients do not maintain authoritative copies of these records.

\textbf{Supabase Storage.} The private \texttt{backtests} bucket stores JSON backtest reports as durable object artifacts. After computing a simulation, the backtest path attempts to generate a local JSON file and, when generation succeeds, automatically attempts to upload that file with replacement enabled. The local protected route remains available when cloud upload fails, and an artifact-generation or upload exception does not invalidate the completed simulation. For successfully persisted objects, the backend can list the available JSON reports and return an authenticated proxy path; it does not expose a public bucket URL.

\textbf{Redis.} Redis stores temporary server-side authentication and verification state, including access and refresh sessions, verification or reset OTPs, failed-attempt counters, resend cooldowns, and one-time reset-session mappings. Time-to-live (TTL) expiration removes these values automatically, and server-side session records allow issued tokens to be revoked; Redis is not a source of permanent user or financial data \cite{redisDataTypes2026}. Access and refresh sessions use \texttt{session:access:\{user\_id\}} and \texttt{session:refresh:\{user\_id\}}, while OTPs and failed-attempt counters use \texttt{otp:\{purpose\}:\{email\}} and \texttt{otp:attempts:\{purpose\}:\{email\}}. Under the current configuration, an OTP is valid for 15 minutes with at most five failed attempts. Successful password-reset verification creates a five-minute one-time reset session and invalidates an older session through the reverse mapping.

\textbf{Expo SecureStore.} On the mobile device, Expo SecureStore protects the access and refresh tokens under \texttt{access\_token} and \texttt{refresh\_token}. It also holds small device-local preferences such as onboarding completion, theme, language, and the saved analysis configuration \cite{expoSecureStore2026}. Tokens are removed when refresh fails or the user signs out. Favorites, investment horizon, chat history, and financial records are requested from the backend rather than stored as an authoritative local database, preventing a stale device value from being treated as confirmed server state.

The acquisition pipelines and storage boundaries together provide a stable evidence layer for the analytical components. Live and offline processes normalize heterogeneous sources before they reach application services; relational links preserve stock, industry, article, and user context; and short-lived secrets remain outside durable business tables.
