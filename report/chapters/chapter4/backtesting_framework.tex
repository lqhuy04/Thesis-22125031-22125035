\section{Backtesting Framework}
\label{sec:backtesting-framework}

Stockrium includes a historical simulation subsystem for evaluating whether the analytical pipeline behaves consistently with its intended decision rules. The subsystem is designed as an engineering and research tool rather than an automated trading facility. It reuses the production multi-agent components and the same deterministic technical-scoring implementation, applies explicit execution assumptions, and produces machine-readable artifacts for later evaluation. Experimental results obtained from this framework are reported in Chapter~6.

Established Python frameworks already provide reusable data feeds, strategy lifecycles, order simulation, indicators, portfolio accounting, and fast parameter exploration. For example, Backtrader provides an event-driven strategy and broker abstraction \cite{backtraderDocs2026}, while VectorBT emphasizes vectorized analysis over pandas and NumPy objects \cite{vectorbtDocs2026}. Stockrium nevertheless implements a focused simulator because the object being evaluated is not only a conventional deterministic trading strategy. Each historical candidate must reconstruct a date-bounded production request, invoke the same enabled specialist agents, recommendation node, and structured aggregator used by the application, and apply the fixed weighted-score and minimum technical-score decision gates. The surrounding evaluation framework then simulates accepted decisions, constructs explicit technical and passive comparators, and returns their artifacts through the existing FastAPI and Supabase workflow. The aggregator's confidence is retained for later grouping and statistical analysis but does not admit or reject a candidate.

Adapting a general framework would still require custom adapters for historical workflow state, language-model outputs, source-availability markers, shared production scoring, and Stockrium's stored result schema. A compact in-project framework makes these assumptions visible and allows exact correspondence with the production decision path to be tested. The trade-off is that mature frameworks provide broader execution, portfolio, optimization, and broker features that the current simulator does not reproduce. Thus, the custom implementation is justified by production-path fidelity and experimental traceability, not by a claim that general frameworks are inadequate; cross-checking future deterministic results with an established engine remains desirable.

The implementation is exposed through the access-controlled internal \texttt{POST} \path{/api/agentic/backtest} endpoint. A request specifies the stock symbol, optional inclusive historical boundaries, benchmark index name, maximum holding period, optional score-based exit, and automatic or manual evidence selection; the normalized technical threshold is fixed internally at 0.6. Daily stock OHLCV data are loaded through the market service, while daily values for the selected benchmark index---\texttt{VNINDEX} by default---provide the reference series for regime analysis. Each completed run returns model decisions, simulated trades, metrics, benchmark comparisons, statistical tests, and visualization data.

\subsection{Evaluation Architecture}
\label{subsec:backtest-evaluation-architecture}

The evaluation architecture separates the full production-path simulation from four explicit comparison flows: an engine-only technical baseline, a same-security buy-and-hold reference, a random-entry benchmark, and five single-indicator ablations. These flows share historical stock data and common accounting definitions where appropriate, but they answer different questions and should not be interpreted as interchangeable trading strategies. The selected benchmark index is used only for regime analysis; it does not contribute to stock-indicator scoring or candidate selection.

The full-pipeline flow in Figure~\ref{fig:backtest-execution-flow} reuses the production indicator service, shared binary-scoring rules, enabled specialist agents, deterministic recommendation node, and structured aggregator rather than introducing a research-only prediction model. Historical candles are converted into the five indicator scores, after which the combined or manually selected score is normalized and tested against the fixed 0.6 technical gate. Only passing dates invoke the date-bounded specialist branches. Technical evidence ends at the candidate date, article retrieval uses its historical upper bound, and the fundamental branch excludes annual rows from the simulated year and future years. The enabled branches converge before the deterministic recommendation applies the configured weights and Buy-or-Wait constraints. The aggregator preserves that decision and adds a bounded confidence value and explanation; confidence is not an execution gate.

A candidate proceeds to trading only when the established decision is \textit{Mua} (Buy). The recommendation-generated stop-loss, take-profit, and positive holding-period override are transferred to the signal. The stop-loss and take-profit boundaries are then checked against the next tradable open; if the open has already crossed either boundary, the plan is treated as no longer executable and no trade is created, although the decision remains in the stored artifact. Otherwise the simulator enters at the next open and applies the recommendation-generated boundaries, the optional score-drop exit, or the holding-period timeout. A missing or nonpositive holding override falls back to the request-level limit. VN-Index observations join only at the later regime-analysis stage.

The engine-only flow in Figure~\ref{fig:backtest-engine-only-flow} begins from the same scored daily frame and retains every date that passes the normalized technical gate as a signal. It does not call the specialist, recommendation, or aggregator nodes and therefore has no recommendation-generated stop-loss, take-profit, or holding-period override. It uses the request-level holding limit, the same next-open convention and transaction-cost model, and the optional score-drop exit when enabled. Candidate signals that arise while a same-symbol position remains open do not create overlapping positions. Its output supplies the deterministic technical baseline used beside the full-pipeline result. Because the full pipeline changes both candidate acceptance and trade management, their observed difference measures the combined Buy-or-Wait and trading-plan layer rather than filtering alone.

The same-security buy-and-hold flow in Figure~\ref{fig:backtest-buy-hold-flow} is a passive reference calculated independently for each evaluated security. It enters at the first open in the evaluation frame and exits at the final close, producing the ratio of final close to first open minus one. The implementation does not deduct the simulator's transaction cost from this reference. Buy-and-hold therefore represents continuous exposure to the same security rather than an exposure-matched replication of the pipeline's intermittent positions.

The random-entry benchmark in Figure~\ref{fig:backtest-random-entry-flow} evaluates whether the pipeline return could be reproduced by entry timing without analytical selection. For each security, one simulation samples as many signal dates as the number of completed full-pipeline trades, or one date when the pipeline completes no trade. The sampled signals enter at the next open, use a fixed 20-candle maximum hold, incur the same transaction cost as the simulator, and receive no recommendation-generated price boundaries. Non-overlap handling may reduce the number of random trades actually executed. Repeating this procedure 1,000 times produces a distribution of total returns from which the pipeline's percentile rank and the stored random-entry p-value are derived.

The single-indicator ablations in Figure~\ref{fig:backtest-single-indicator-flow} are companion experiments rather than branches invoked during every full-pipeline run. Their runner loads pre-start history, calculates the same five indicator families and shared binary-score columns, preserves the 50-candle warm-up, and trims to the requested evaluation interval only after scoring. One score column is then selected at a time; every eligible date with a value of one becomes a candidate for the corresponding RSI, MACD, KDJ, Bollinger Bands, or moving-average experiment. Each ablation runs independently without language-model calls, using next-open entry, the fixed 20-candle hold, and the same per-side transaction cost. The resulting metrics and artifacts show how outcomes vary when candidate construction depends on only one technical perspective.

The five scoring rules are implemented once in a shared deterministic module. The production technical node uses this module to build indicator-level explanations, while the historical and ablation adapters write the same returned values into score columns. This shared implementation prevents drift between interactive analysis and historical evaluation; unit tests cover the scoring rules and their adapters rather than comparing separately maintained formulas at runtime.

\subsection{Technical Signal Construction}
\label{subsec:backtest-signal-construction}

The historical indicator engine calls the same indicator service as the production technical node for the five indicator families and periods described in Section~\ref{subsubsec:technical-analysis-node}: RSI with a 14-period lookback, SMA20 and SMA50, 20-period Bollinger Bands at two standard deviations, MACD $(12,26,9)$, and KDJ with a 9-period range and 3-period smoothing. Each perspective contributes either zero or one point, giving a combined score $s_t\in[0,5]$ when all indicators are enabled.

The scoring engine marks the first 50 loaded observations as a warm-up interval because SMA50 is the longest rolling feature. When a request supplies a later evaluation start date, the service retains the earlier daily history while calculating indicators and trims the scored frame only afterward; this avoids resetting rolling and exponential indicators at the requested boundary. The single-indicator ablation runner follows the same ordering: it loads pre-start history, preserves the shared 50-candle warm-up when selecting one score column, and trims only the scored frame. Its artifacts record both the warm-up length and whether pre-start history was loaded. The production technical threshold is fixed at $0.6$. With all five indicators enabled, this is equivalent to the normalized threshold $\tau=3$ on the five-point scale. A candidate is emitted on every eligible date,

\begin{equation}
    \mathrm{candidate}_t =
    \mathbb{I}\!\left(s_t \geq 3\right).
    \label{eq:backtest-technical-gate}
\end{equation}

When manual mode enables $m$ indicators, their binary-score sum is multiplied by $5/m$ before applying the same threshold, so the required proportion remains $0.6$ for any selection from one to five indicators. The last candle is never executed because no next-candle entry price exists. Model-backed analysis is invoked on dates that pass this fixed technical gate. Technical and article plans use the candidate date as their upper boundary and the same 365-day and 90-day windows, respectively, as the production mid-term analysis flow.

Equation~\ref{eq:backtest-technical-gate} is an author-defined Stockrium eligibility rule rather than a signal formula taken from an external strategy. It mirrors the deterministic production requirement that technical score must be at least $0.6$ before a Buy decision is possible.

\subsection{Trade Simulation and Cost Model}
\label{subsec:backtest-trade-simulation}

The simulator is long-only and permits at most one open position per symbol. A signal completed after candle $t$ is always entered at the open of candle $t+1$, avoiding execution at the same close used to construct the signal. The recommendation's \texttt{entry\_price}, which is based on the signal-date close in a historical run, is retained in the decision artifact for audit but does not override this executable next-open price. Finite take-profit and stop-loss levels and a positive maximum-holding override are copied from the recommendation onto the signal. If the next open is at or beyond either supplied price boundary, the signal is skipped because the original plan is no longer executable; otherwise those levels are retained, and a missing or nonpositive holding override falls back to the request's configured maximum.

Starting with the entry candle, which counts as the first held candle, the daily low is checked against the stop-loss level and the daily high against the take-profit level. Stop loss is evaluated first, giving a conservative outcome when both levels fall within one daily bar and intraday order is unavailable. If score-based exit is enabled, a score below three schedules a \texttt{SIGNAL\_EXIT} at the following open only when that following candle remains inside the maximum-holding window. If no earlier exit occurs, the position closes at the final permitted close with reason \texttt{TIMEOUT}. The scan resumes from the exit candle, so same-symbol positions do not overlap.

The default transaction cost is $c=0.0015$, or 0.15\% per side. This value is defined by the backend and is not exposed as a request field in the backtest API. For entry price $P_k^{\mathrm{in}}$ and exit price $P_k^{\mathrm{out}}$, net return is

\begin{equation}
    r_k = \frac{P_k^{\mathrm{out}}-P_k^{\mathrm{in}}}{P_k^{\mathrm{in}}}-2c.
    \label{eq:backtest-net-trade-return}
\end{equation}

The default round-trip deduction is therefore 0.30\%. The simulation does not separately model bid--ask spread, market impact, partial fills, taxes, price-limit queues, or gap slippage at exit. These assumptions are considered when interpreting the experimental results.

Equation~\ref{eq:backtest-net-trade-return} is the framework's accounting definition of simulated net trade return. The value $c=0.0015$ is a backend modeling assumption per side, not a claim that every Vietnamese investor incurs one universal statutory fee. Keeping it explicit in the implementation allows later controlled experiments to replace it with broker-, tax-, liquidity-, or period-specific costs without exposing it as an end-user API option.

\subsection{Measures, Benchmarks, and Artifacts}
\label{subsec:backtest-metrics-tests}

The framework reports trade count, win rate, average and median trade return, total compounded return, annualized return, maximum drawdown, a trade-level Sharpe statistic, Calmar ratio, profit factor, and exit counts. Total return and the post-trade equity sequence are

\begin{equation}
    R_{\mathrm{total}}=\prod_{k=1}^{K}(1+r_k)-1,
    \qquad
    E_k=\prod_{j=1}^{k}(1+r_j).
    \label{eq:backtest-total-return}
\end{equation}

Let $H_k=\max_{j\leq k}E_j$ denote the running peak. Maximum drawdown is the minimum of $(E_k-H_k)/H_k$. The implemented Sharpe statistic is

\begin{equation}
    S=\sqrt{K}\frac{\overline{r}}{s_r},
    \label{eq:backtest-sharpe}
\end{equation}

where $s_r$ is the sample standard deviation of trade returns. It follows the risk-adjusted comparison principle of the Sharpe ratio \cite{sharpe1994ratio}, but is scaled by trade count rather than a fixed annual frequency. It is therefore an internal comparison statistic rather than a conventional annualized portfolio Sharpe ratio.

Equation~\ref{eq:backtest-total-return} and the stated maximum-drawdown calculation are implementation definitions based on geometric compounding of sequential trade returns and decline from the running equity peak. Equation~\ref{eq:backtest-sharpe} is explicitly adapted from Sharpe's risk-adjusted comparison principle, with the nonstandard $\sqrt{K}$ trade-count scaling identified above. Stating these origins separates standard financial concepts from Stockrium-specific event, cost, and scaling choices.

The evaluation suite compares the full pipeline with the engine-only strategy, buy-and-hold exposure, and 1,000 random-entry simulations. The buy-and-hold reference is the last close divided by the first open minus one and does not receive the simulator's transaction-cost deduction. Each random simulation samples as many signal dates as the number of executed full-pipeline trades (or one date when the full pipeline has no trade); subsequent overlap handling can reduce the number actually executed. It applies the same transaction cost and currently uses a fixed 20-candle maximum hold regardless of the request's holding limit. The suite also provides a one-sample $t$-test, a 1,000-draw sign-permutation test, a Pearson score--return information coefficient, and one-way analysis of variance across confidence tiers. Numeric confidence is grouped as high for values at least 0.70, medium for values from 0.55 to below 0.70, and low otherwise. Benchmark-index regimes are based on the 60-session return: above 15\% is an uptrend, below $-15\%$ is a downtrend, and the remainder is sideways. Because the benchmark frame is currently trimmed at the evaluation start before this return is calculated, the first 60 sessions have no lookback value and are also assigned to the sideways group. Because repeated strategy comparisons can overfit historical data \cite{bailey2017pbo}, the framework retains negative and non-significant results instead of reporting only successful securities.

Each run produces visualization JSON containing prices, indicators, decisions, entries, exits, metrics, and the effective pipeline configuration. The artifact is written to the local visualization directory, can be served by FastAPI, and is uploaded to Supabase Storage when that optional step succeeds. For a symbol that belongs to the currently resolved VN30 universe, a separate local aggregate JSON file is upserted for VN30-level analysis; non-members are skipped. Chapter~6 uses these saved artifacts as the quantitative evidence for evaluation.
