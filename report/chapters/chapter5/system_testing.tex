\section{Testing Objectives and Evidence Boundary}
\label{sec:testing-objectives-evidence}

System testing examines whether the implemented Stockrium components follow their software contracts and support the intended user workflows. For the mobile application, this means accessing prepared market information, configuring an analysis, and maintaining a conversation. For Stockrium Lab, it means allowing an authenticated user to run an analysis or backtest, retain the resulting experiment, monitor its state, reopen its details, and compare compatible runs. These questions are distinct from whether a recommendation will be profitable. Historical outcomes are examples produced by the tool and are discussed separately in Chapter~6; they are not acceptance criteria for Chapter~5.

The principal reproducible evidence in the repository is the Python \texttt{unittest} suite under \path{backend/tests}. Static inventory of the current revision identifies 106 test methods across 20 files. The tests use fixed values and mocks at external boundaries so deterministic application behavior can be checked without making regression success depend on SSI, Supabase, Redis, email, or language-model availability. The repository does not contain a machine-readable test-run log, coverage report, device matrix, browser-automation report, load-test report, or archived manual-test protocol for the current revision. Therefore, the inventory above demonstrates implemented test coverage but is not presented as 106 recorded passes. The repeatable backend command is \texttt{python -m unittest discover -s tests -v} from the \path{backend} directory. A release record should preserve its console output together with the revision identifier, Python version, execution date, and dependency versions. This evidence boundary prevents planned, source-inspected, or previously observed behavior from being reported as a newly executed test result.

\section{Automated Backend Verification}
\label{sec:automated-backend-verification}

The automated suite emphasizes deterministic boundaries where a regression can be identified from a fixed expected value. External calls are mocked where appropriate, while tests exercise the service, workflow, persistence adapter, and route logic surrounding those calls. This approach verifies how Stockrium handles model outputs and provider failures without claiming that a mocked response measures live-provider quality.

\subsection{Historical Simulation and Security Boundaries}
\label{subsec:simulation-security-testing}

The historical-simulation tests cover the shared technical rules, preservation of pre-start history and the 50-candle warm-up, date trimming, benchmark retrieval, next-open entry, plan-boundary rejection, score exits, holding limits, non-overlapping positions, transaction costs, and visualization configuration. Additional tests ensure that legacy walk-forward output is not exposed and that VN30 aggregate statistics retain only the latest resolved universe. These assertions verify internal consistency of the simulator; they do not use a positive return as a passing condition.

Security tests complement this behavior. They reject oversized or malformed requests, unsafe database queries, plaintext OTP storage, path traversal, and unauthenticated Stockrium Lab access. They also confirm the changed authorization model: Lab routes require a valid user session but do not require an administrator role, while experiment and artifact reads remain isolated by owner. Authentication tests cover refresh-token rotation, independent multi-device Redis keys, and logout of one selected session without revoking another session belonging to the same user.

\section{Securities Analyst Feedback}
\label{subsec:securities-analyst-feedback}

Ms.~Trinh, a securities analyst at FPT Securities Joint Stock Company, provided qualitative professional feedback on Stockrium \cite{trinh2026weights}. She explained that manually combining fundamental information, technical indicators, and relevant news can require several hours and may take a new investor longer. Her feedback supported the application's objective of organizing these evidence sources and presenting an understandable starting point for further investigation; it was not used to claim that the generated decision replaces professional judgment.

The consultation also influenced the analysis design. The team refined horizon-dependent weights, technical intervals, and evidence windows, while fundamental analysis was changed to retain up to five valid annual periods regardless of the selected horizon. Financial and nonfinancial companies were separated because their balance-sheet structures and relevant indicators differ: nonfinancial analysis emphasizes liquidity, leverage, efficiency, profitability, valuation, and available DuPont components, whereas financial-sector analysis uses capital safety, asset quality and management, earnings, liquidity, and P/B-oriented valuation.

Ms.~Trinh considered the interface visually accessible, the available stock information sufficiently comprehensive, and the AI explanations understandable. She also tried multiple chatbot questions reflecting practical stock and market information needs. These observations provide one expert perspective on usability and domain appropriateness, but they are not a controlled user study, a comparison with competing products, or evidence of profitable recommendations.

\section{Testing Summary and Limitations}
\label{sec:testing-summary-limitations}

The current repository provides substantial automated coverage of the most important deterministic backend boundaries, including the multi-agent decision flow, historical simulation, authenticated experiment lifecycle, comparison constraints, reproducibility disclosures, and cross-user artifact isolation. This coverage is aligned with Stockrium's revised contribution because it tests whether the experimentation tool behaves transparently and preserves user-owned results.

The remaining evidence gaps are explicit. The current revision has no archived execution log or measured statement coverage, no automated client tests, no recorded browser or Android compatibility matrix, no load or endurance results, and no durable-queue recovery test. Live AI and upstream financial providers are intentionally not used as regression oracles. Most importantly, software-test success establishes implementation correctness only; it does not establish predictive validity, financial superiority, or future profitability.
