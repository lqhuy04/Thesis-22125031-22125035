\section{Testing Objectives and Evidence Boundary}
\label{sec:system-testing-objectives}

System testing in this chapter evaluates whether selected Stockrium backend behaviors conform to the implemented contracts. Unlike Chapter~6, which examines historical investment outcomes, the tests here target software behavior: multi-agent routing, structured analysis, deterministic scoring and decision boundaries, authentication and input guards, and backtesting mechanics.

Only results that can be reproduced from artifacts in the repository are reported as executed. The evidence base is the automated Python suite under \texttt{backend/tests}; it contains 66 tests and is executed from \texttt{backend/} with:

\begin{center}
\small\texttt{python3 -m unittest discover -s tests -p 'test\_*.py' -q}
\end{center}

The repository does not contain a k6 script or raw load-test summary, a Postman collection, a complete manual test-case ledger, an archived Android device matrix, or a signed user-acceptance record. Consequently, this chapter does not present response-time percentiles, device or usability pass counts, or a claim that 104 manual cases were executed. These remain important validation activities, but reporting them as completed without their supporting artifacts would not be auditable.

\section{Testing Method and Environment}
\label{sec:testing-methods-environment}

The suite uses Python's \texttt{unittest} framework. External model calls, database-dependent lookups, and selected analysis nodes are replaced with \texttt{unittest.mock} objects where a deterministic boundary is required. Temporary directories isolate generated report files. Fixed pandas data frames and explicit structured dictionaries supply historical candles, specialist outputs, recommendation plans, and benchmark values, so test success does not depend on a live Supabase, SSI, OpenAI, or DeepSeek response.

This design is appropriate for checking deterministic rules and failure containment. It can verify, for example, that an invalid model plan is replaced by the correct horizon fallback, that disabled branches are not invoked, and that an order is not entered when the next open has already crossed a plan boundary. It does not verify the availability, latency, or factual quality of a live external provider. The test run used the project's backend Python environment; no Android or browser client was started by this command.

The specialist-node tests confirm the implementation distinction described in Chapters~2 and~4. News and fundamental analysis obtain normalized scores from structured model output, whereas the technical score is calculated from the deterministic earned-point ratio and the technical model call supplies narration only. Recommendation tests exercise the weighted total and minimum technical threshold independently; confidence produced later by the aggregator cannot change the Buy-or-Wait result.

Security coverage is deliberately specific rather than equivalent to a penetration test. The suite checks the read-only SQL guard against file, configuration, sleep, user-table, multi-statement, and excessive-limit queries; validates size, pattern, language, and selection boundaries in representative request models; confirms that OTP values are hashed; and verifies that the unsafe administrator-login path is absent. It does not provide third-party security certification or network-level attack coverage.

The 100\% rate applies only to this selected automated suite and its mocked or fixed inputs. It does not measure statement or branch coverage, prove that every FastAPI route works against live infrastructure, validate OpenAI or DeepSeek factual quality, or establish Android presentation and navigation behavior. No automated frontend test suite is currently present. Load, long-duration ingestion, accessibility, localization, physical-device compatibility, and observed user acceptance also remain outside the repository-verifiable evidence.

A stronger release-validation package should preserve the exact tested revision and environment, archive machine-readable unit and API results, add isolated Supabase and Redis integration fixtures, and retain a complete requirement-to-test ledger. Android end-to-end tests should then cover authentication, search, stock details, favorites, analysis, and chat. Performance testing should be reported only after the workload script and raw summary are versioned, and any user-acceptance statement should reference participant protocol and signed or dated observations.

\section{Chapter Summary}
\label{sec:system-testing-summary}

Stockrium's repository contains 66 reproducible automated backend tests, all of which passed in the recorded run. The evidence covers multi-agent routing and structured outputs, deterministic scoring and decision rules, selected security and validation guards, authentication refresh rotation, and the principal backtesting boundaries used by Chapter~6. The result supports these implemented behaviors under fixed and mocked conditions, but it is not presented as evidence of unrecorded load, mobile-device, manual black-box, or user-acceptance testing.
