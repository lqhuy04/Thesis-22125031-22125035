\section{Testing Objectives and Scope}
\label{sec:system-testing-objectives}

System testing evaluated whether Stockrium satisfies its functional requirements as an integrated mobile--backend platform. Unlike Chapter~6, which examines investment-strategy performance, this chapter focuses on software correctness, integration, security, responsiveness, reliability, usability, and device compatibility.

A black-box, requirement-oriented approach compared each observed result with a predefined acceptance criterion. Tests included valid flows and negative or boundary cases such as invalid inputs, unauthorized access, expired sessions, duplicate records, empty data, and connection failures. \section{Testing Methods, Tools, and Environment}
\label{sec:testing-methods-environment}

\subsection{Testing Methods and Tools}

Manual black-box testing checked complete user flows and visible error states. Postman and Swagger UI were used to inspect FastAPI status codes, response bodies, validation, and authorization independently of the mobile client. Expo development builds ran on physical devices and emulators. User acceptance testing involved the developers and Ms.~Trinh, an FPT Securities analyst, who reviewed workflow clarity, financial terminology, and presented information. A k6 constant-virtual-user scenario generated the concurrent performance workload \cite{k6Scenarios2026}.

\subsection{Test Environment and Data}

The backend used Python~3.12 and FastAPI~0.128.0; the client used Expo SDK~54 and React Native~0.81.5. Mobile tests ran on a Pixel~7 Android~15 emulator, Samsung Galaxy A54 (Android~14), iPhone~15 iOS~18 simulator, and iPhone~13 (iOS~18).

Test accounts included verified, unverified, secondary, and administrator users. Representative data covered securities, company profiles, financial statements, news, favorites, portfolios, search histories, risk preferences, and chats. VNM, FPT, and VCB supplied complete positive cases; unknown symbols, missing fields, expired tokens, invalid OTPs, duplicate favorites, and empty ranges supplied negative cases. AI outputs were assessed for schema validity, completeness, consistency, and safe presentation rather than investment profitability.

\section{Non-Functional Testing}
\label{sec:non-functional-testing}

\subsection{Performance and Reliability}

Performance tests measured user-perceived response time under stable broadband with 20 concurrent virtual users. After a two-minute ramp-up, the workload remained at 20 users for 15 minutes and mixed authentication, market/search reads, stock-detail requests, and selected AI/chat calls. Two otherwise equivalent runs were compared: an off-session baseline with the market stream stopped, and a trading-session run in which the one-minute stock-price stream, daily-price stream, and market-index stream were active and flushing completed candles to Supabase. Limits were two seconds for ordinary APIs, fifteen seconds for agentic AI analysis, and ten seconds for chat.

All operations met their limits in both runs. The active collectors increased p95 latency by 5.6--21.5\%, with the largest relative effect on market/search reads because those requests share Supabase and network resources with live candle persistence. No unexpected HTTP error exceeded 1\%, and no completed one-minute candle was missing from the post-run database check. The separation of SSI callbacks from the candle-flush loop prevented database writes from blocking stream ingestion, while sequential post-session reconciliation was not started during this trading-session test.

These results show that the tested prototype tolerated a moderate 20-user workload while live collection was active; they do not establish capacity beyond that level or under production-scale traffic. Loading feedback remained visible and submitted actions were disabled to prevent duplicates. During interrupted connections, expired sessions, empty upstream data, and provider outages, the application preserved its state, offered retry or error feedback, and recovered after service restoration. Four reliability cases passed.

\section{Chapter Summary}
\label{sec:system-testing-summary}

Stockrium was evaluated through 108 functional, integration, non-functional, and compatibility cases using manual testing, Postman/Swagger UI, Expo devices/emulators, and user acceptance testing. All cases passed: features produced expected results, integrations returned valid responses, security controls rejected invalid access, response times met their limits, and the application operated correctly across the tested platforms, themes, screen sizes, and languages.
