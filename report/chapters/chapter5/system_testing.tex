\section{Testing Objectives and Scope}
\label{sec:system-testing-objectives}

System testing was conducted to determine whether the implemented Stockrium platform satisfies its functional requirements and operates correctly as an integrated mobile and backend system. Unlike Chapter~6, which evaluates the historical behavior of the investment-analysis strategy, this chapter evaluates software correctness: whether users can complete the intended tasks, whether the APIs and external services exchange valid data, and whether the application remains secure, responsive, reliable, and usable on the supported devices.

The tests followed a black-box, requirement-oriented approach. Each test supplied an input or user action, observed the externally visible result, and compared it with the corresponding acceptance criterion. Both valid and invalid inputs were included. Valid cases confirmed the main user flows, while negative and boundary cases examined form validation, missing data, unauthorized access, expired sessions, duplicate records, empty responses, and temporary connection failures. The complete scope is summarized in Table~\ref{tab:test-scope}.

The scope covers the complete user-facing system from account creation to AI-assisted stock analysis and follow-up conversation. It also covers the principal integration boundaries on which the application depends. Historical profitability and comparisons among investment strategies are intentionally excluded because they belong to the experimental evaluation in Chapter~6. Source-code unit coverage, penetration testing by a third party, and large-scale production load testing were also outside the scope of this prototype evaluation.

The acceptance rule was that every critical user flow had to complete without a blocking defect, the actual result of every case had to match its expected result, protected resources had to reject invalid access, and the measured response times had to remain within the thresholds defined before execution. A case was recorded as passed only after its result had been observed on the running system.

\section{Testing Methods, Tools, and Environment}
\label{sec:testing-methods-environment}

\subsection{Testing Methods and Tools}

Four complementary methods were used. Manual black-box testing verified the application from the user's perspective without relying on the implementation of individual functions. Postman and FastAPI's generated Swagger UI exercised backend endpoints directly and made it possible to inspect status codes, response bodies, authorization headers, and validation errors independently of the mobile interface. Expo, physical devices, and Android/iOS emulators were used to execute the mobile application under different platform and display conditions. Finally, user acceptance testing was performed with the project developers and Ms.~Trinh, an FPT Securities analyst, to assess whether the terminology, workflows, and presented financial information were appropriate for the intended context.

The authentication cases verified the full account state transition rather than treating sign-in as an isolated operation. A newly registered account could not sign in before email verification. The current OTP completed verification, whereas incorrect and expired values did not. After sign-in, an expired access token caused one coordinated refresh and the interrupted request was retried. Logout removed the local session and prevented subsequent access to protected screens. These results confirmed that the visible mobile state remained consistent with the backend session state.

Market and stock-detail testing confirmed that a symbol selected from search, watchlist, industry movement, market highlights, or related stocks opened the same company context. Price periods and indicator selections updated the chart without changing the selected symbol. Empty search and unavailable-data cases preserved the screen structure and showed a meaningful empty or error message instead of an indefinite loading state. Long article content, financial tables, and chart guides remained scrollable and did not block the primary actions.

The AI-analysis cases examined both configuration and presentation. Automatic mode produced an analysis using the system-selected evidence. Manual mode accepted only configurations containing at least one enabled source; enabled technical and fundamental groups also required a selected subcategory. The displayed recommendation contained the expected symbol, evidence summaries, normalized scores, confidence, action, and explanation. Users could continue from this result into a seeded chatbot conversation without losing the initial analysis context.

User-owned information remained consistent after screen refresh and application restart. Favorites, risk appetite, portfolios, search history, and conversations were associated with the authenticated account. Repeating an add operation did not create a visibly duplicated favorite, and deleting a chat removed it from both the session list and its history route. All 48 functional cases produced the expected visible result.

The 100\% result should be interpreted within the stated scope. It demonstrates conformance to the selected requirements and environments, but it does not prove the absence of defects under every possible device, network, data record, or provider behavior. External SSI and language-model services may change their availability, latency, or response behavior after the test period.

Despite these limitations, the tests cover the highest-risk paths of the prototype: account and session management, protected and owner-scoped data, real market information, financial visualization, structured agentic analysis, conversation, and bilingual mobile presentation. The system therefore met its software acceptance criteria and was considered sufficiently correct, integrated, secure, responsive, compatible, and usable for the subsequent experimental evaluation and thesis demonstration.

\section{Chapter Summary}
\label{sec:system-testing-summary}

This chapter evaluated Stockrium through functional black-box, integration/API, non-functional, and compatibility/device testing. Manual testing, Postman and Swagger UI, Expo with devices and emulators, and user acceptance testing were applied to 108 test cases. All cases passed: principal features produced their expected results, external and persistent-data integrations returned valid responses, security controls rejected invalid access, measured response times remained within their limits, and the application operated correctly across Android/iOS, screen sizes, themes, and Vietnamese/English localization. These results establish that the implemented platform satisfies the defined system requirements within the tested prototype scope.
